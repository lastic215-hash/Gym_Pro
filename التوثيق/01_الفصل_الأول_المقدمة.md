# الفصل الأول: مقدمة الدراسة التمهيدية

## 1.1 فكرة المشروع

### 1.1.1 تعريف بالنظام القائم

تعتمد غالبية صالات الألعاب الرياضية (الجيم) في ليبيا على أنظمة يدوية أو أوراقية لإدارة عملياتها اليومية. يشمل النظام القائم عادةً على سجلات ورقية لتسجيل الأعضاء، وجدول يدوي لتتبع الحضور، ودفتر مالي لتسجيل المدفوعات. تتم عمليات تجديد الاشتراك والتقارير المالية يدوياً من قبل موظفي الاستقبال أو المدير.

تتضمن الأدوات المستخدمة حالياً في معظم الصالات:
- سجلات ورقية لبيانات الأعضاء
- آلة حاسبة لحساب المدفوعات
- ملفات Excel محدودة للتقارير
- لا يوجد نظام مركزي لإدارة البيانات

### 1.1.2 مشاكل النظام القائم

يواجه النظام القائم عدة مشاكل جوهرية تؤثر على كفاءة إدارة الصالة:

**مشاكل إدارية:**
- صعوبة تتبع اشتراكات الأعضاء يدوياً مما يؤدي إلى فقدان أعضاء
- عدم الدقة في حساب المدفوعات والإيرادات
- صعوبة إعداد التقارير المالية في الوقت المناسب
- فقدان البيانات في حالة فقدان السجلات الورقية

**مشاكل تشغيلية:**
- بطء عمليات التسجيل وتجديد الاشتراك
- عدم khảية البحث السريع عن بيانات العضو
- صعوبة تتبع حضور الأعضاء والمدربين
- عدم وجود نظام إنذار لانتهاء الاشتراكات

**مشاكل مالية:**
- صعوبة التحقق من دقة المبالغ المحصّلة
- عدم وجود تطابق بين الخزينة الفعلية والمتوقعة
- صعوبة تتبع المصروفات وتصنيفها
- عدم القدرة على تحليل الربحية بشكل دقيق

### 1.1.3 تعريف النظام المقترح (GYM Pro)

GYM Pro هو نظام متكامل لإدارة صالات الألعاب الرياضية مبني بتقنية Electron وExpress.js وMySQL. يعمل النظام كتطبيق سطح مكتب (Desktop Application) يعمل بشكل أساسي على الإنترنت المحلي مع إمكانية المزامنة السحابية.

**الميزات الأساسية للنظام:**
- واجهة عربية بالكامل مع دعم RTL (من اليمين لليسار)
- يعمل بدون إنترنت (Offline-First) مع مزامنة تلقائية
- نظام أدوار متعدد (مدير، موظف استقبال، مدرب)
- لوحة تحكم تفاعلية مع رسوم بيانية
- إدارة شاملة للأعضاء والباقات والمدفوعات
- نظام حضور متقدم للمدربين
- إغلاق يومي مالي مع مطابقة الخزينة
- تقارير مالية مفصلة

### 1.1.4 أهداف المشروع

**أهداف عامة:**
- تطوير نظام إلكتروني شامل لإدارة صالة الألعاب الرياضية
- تحسين كفاءة العمليات اليومية و giảm الوقت المستغرق
- توفير تقارير مالية دقيقة ودقيقة
- تحقيق رضا الأعضاء من خلال تحسين تجربتهم

**أهداف تفصيلية:**
- تسجيل الأعضاء وإدارة بياناتهم بشكل إلكتروني
- إدارة الباقات والاشتراكات وأسعارها
- تسجيل المدفوعات وإصدار الإيصالات
- تتبع حضور الأعضاء والمدربين
- إعداد التقارير المالية اليومية والأسبوعية والشهرية
- إدارة المصروفات وتصنيفها
- إغلاق الوردية اليومية مع مطابقة الخزينة

### 1.1.5 مزايا النظام المقترح

| الميزة | الوصف |
|--------|-------|
| يعمل بدون إنترنت | Offline-First: البيانات محفوظة محلياً حتى عند انقطاع الإنترنت |
| مزامنة سحابية | تلقائي: عند عودة الإنترنت يتم مزامنة البيانات مع Railway Cloud |
| واجهة عربية RTL | تصميم عربي بالكامل مناسب للسوق المحلي |
| نظام أدوار | مدير + موظف استقبال + مدرب، كل دور له صلاحياته |
| لوحة تحكم تفاعلية | رسوم بيانية وإحصائيات محدثة لحظياً |
| أمان البيانات | Parameterized Queries ضد SQL Injection |
| سهولة الاستخدام | واجهة بسيطة وواضحة لا تتطلب تدريباً |

### 1.1.6 حدود المشروع

- لا يدعم النظام حالياً إدارة المتجر أو المبيعات
- لا يوجد تطبيق موبايل (نسخة Android/iOS)
- لا يوجد نظام إشعارات SMS أو Email
- لا يوجد نظام حجز أونلاين
- لا يدعم النظام عدة فروع لنفس الصالة

## 1.2 منهجية التصميم (Design Methodology)

### 1.2.1 منهج Waterfall

تم اتباع منهج **Waterfall** (الشلال) في تطوير هذا المشروع، وهو منهج تقليدي يتبع تسلسل ثابت من المراحل:

```
└── 1. تحليل المتطلبات (Requirements Analysis)
    └── 2. التصميم (Design)
        └── 3. التنفيذ (Implementation)
            └── 4. الاختبار (Testing)
                └── 5. الصيانة (Maintenance)
```

**لماذا Waterfall؟**
- المشروع له متطلبات واضحة ومحددة مسبقاً
- فريق التطوير صغير (طالب واحد)
- لا يتطلب مراحل تكرارية كثيرة
- مناسب للمشاريع الأكاديمية

### 1.2.2 مراحل التطوير

| المرحلة | النشاط | الأدوات المستخدمة | المدة |
|---------|--------|------------------|-------|
| تحليل المتطلبات | جمع المتطلبات وتحليلها | المقابلات، الملاحظة | أسبوع |
| التصميم | تصميم قاعدة البيانات والواجهات | MySQL Workbench, Draw.io | أسبوعان |
| التنفيذ | البرمجة والتطوير | VS Code, Node.js | 6 أسابيع |
| الاختبار | اختبار الوحدات والتكامل | Postman, Manual Testing | أسبوعان |
| التوثيق | كتابة التقرير النهائي | Microsoft Word | أسبوع |

## 1.3 دراسة الجدوى (Feasibility Study)

### 1.3.1 الجدوى التقنية (Technical Feasibility)

**البيئة التقنية المطلوبة:**

**المتطلبات المادية (Hardware):**
- حاسوب个人ي بمكونات متوسطة (Intel Core i5, 8GB RAM, 256GB SSD)
- لا حاجة لخوادم مكلفة لأن النظام يعمل محلياً
- لا يحتاج لاشتراك شهري في خدمات سحابية مكلفة

**المتطلبات البرمجية (Software):**
- نظام تشغيل Windows 10/11
- Node.js v18+ (مجاني ومفتوح المصدر)
- MySQL (مجاني)
- Electron (مجاني ومفتوح المصدر)

**البنية التحتية:**
- لا يحتاج لخادم مخصص (Dedicated Server)
- يعمل على شبكة محلية (LAN)
- المزامنة السحابية عبر Railway (خطة مجانية متوفرة)

**النتيجة:** النظام مُجدٍ تقنياً — جميع التقنيات المستخدمة مجانية ومفتوحة المصدر، ولا تحتاج لبنية تحتية مكلفة.

### 1.3.3 الجدوى التشغيلية (Operational Feasibility)

**قابلية الاستخدام:**
- الواجهة عربية بالكامل مناسبة للمستخدم المحلي
- تصميم بسيط وواضح لا يحتاج تدريباً مكثفاً
- يمكن للموظف الجدي تعلم النظام في ساعة واحدة

**التوافق مع البيئة الحالية:**
- يعمل على أجهزة الحاسوب الموجودة في الصالة
- لا يحتاج لتغيير كبير في أنظمة العمل الحالية
- يمكن دمج البيانات القديمة يدوياً

**دعم المستخدمين:**
- واجهة سهلة الاستخدام تقلل الحاجة للدعم الفني
- يمكن للمدير التعامل مع المشاكل البسيطة
- التوثيق المتاح يشرح جميع العمليات

**النتيجة:** النظام مُجدٍ تشغيلياً — سهل الاستخدام ومتوقع قبول المستخدمين له.
